写给产品经理。大模型谁都会接，难的是：改完提示词或换完模型之后，你怎么知道它是真好了，还是碰巧抽到了几条顺的 case。

## 先说结论

评测和调优不是算法组的边角活，是 AI 功能能不能稳定交付的正经事。

做法其实很朴素：

1. 先准备一批固定的测试题（评测集）
2. 约定怎么判对错、看什么指标（评估器）
3. 改 Prompt 或换模型之后，用同一批题再跑一遍（实验）
4. 线上翻车的例子补进题库，下一轮继续考

没有这套流程，所谓「优化」很难验收，也很难排进产品节奏。

## 现在常见的麻烦

多数团队 LLM 功能能上线，但后面会卡在这些地方。

### 1. 改完说不清有没有变好

- 改了一版 Prompt，人工看几条，「好像行了」。
- 换模型、改参数、收紧输出格式，没有固定题库，也没有统一的打分方式。
- 业务问准确率，只能答：「这几个例子过了。」

结果是：优化做了很多，但没法写进验收标准。

### 2. 需求不好排，发版不好卡

- 「优化提示词」排不进迭代：做完看不出涨了多少，也说不清有没有变差。
- 直接上线看反馈，出了问题分不清是 Prompt、模型，还是业务规则。
- 测试发版前不知道该拦哪一版——因为压根没有可重复跑的结果。

### 3. 线上翻车养不活下一轮改进

- 客诉只剩最终结果，当时模型看了什么、回了什么对不上。
- 失败类型进不了题库，下次还是想到哪改哪。
- 一直在修眼前这一单，效果稳不住。

### 4. Prompt 和模型用法太散

- 同一段提示词，代码里一份、文档里一份、某人笔记里又一份。
- 换模型常是救火：哪个能用用哪个，缺对比数据。
- 产品想统一策略，落地时各项目各搞一套。

## 做好了，产品能多拿到什么

| 你多拿到的 | 具体是什么意思 |
|------------|----------------|
| 改动能交差 | 每次大改都能拿出通过率、分项结果，评审有材料 |
| 版本能对比 | 不同 Prompt、不同模型，用同一批题对打 |
| 翻车能复用 | 线上坏例子进题库，下一轮实验会考到 |
| 发布有门槛 | 谁负责、什么分能上线、不行回滚到哪一版，说得清 |

简单讲：评测让你知道「好不好、好在哪」；调优让你知道「下一步改什么」——而且改完还能再验一遍。

## 最少要齐这三样

平台可以后上，但这三样最好先对齐：

| 叫什么 | 人话 | 干什么用 |
|--------|------|----------|
| 评测集 | 固定那批测试题 | 保证大家考的是同一套业务场景 |
| 评估器 | 怎么判对错、怎么打分 | 约定什么叫通过、什么叫严重错误 |
| 实验 | 某版 Prompt / 某模型在这批题上的成绩单 | 证明这次改动值不值得上线 |

再配两样会顺很多：

- **Prompt 版本**：你改的是哪一版，不行回到哪一版。
- **线上调用记录（Trace）**：翻车时能回放输入输出，方便做成新题。

流程可以看成：

```text
线上请求 / 客诉
      │
      ▼
留下能复盘的坏例子（输入 + 输出）
      │
      ▼
补进评测集，定好怎么判分
      │
      ▼
跑实验：对比「改之前」和「改之后」
      │
      ▼
达标再发布；不达标继续改
```

产品上可以立一条规矩：大改 Prompt 或换模型，必须先有实验结论；实验不过，不算优化完成。

## 产品经理怎么推：四步就够

### 第一步：先攒一批正经题

- 从一个真实能力切入，先做 20～50 条也行，关键是每条有对错标准。
- 尽量盖住：正常情况、边界情况、已经翻过的车、安全 / 合规红线。
- 指定维护人：这是产品资产，别变成算法同学电脑里的私有表格。

### 第二步：说清楚怎么判

常见三种，可以混用：

| 类型 | 适合什么 | 要注意什么 |
|------|----------|------------|
| 规则 / 字段比对 | 结构化输出、必填项、枚举是否合法 | 客观、成本低；难评「写得好不好」 |
| 和参考答案比对 | 有标准答案的识别、抽取 | 参考答案要有人持续维护 |
| 再用一个模型来评 | 语义、完整性、语气、合规 | 评判提示词要固定，并抽一部分人工核对 |

产品要拍板两件事：

- **主指标**：比如通过率、关键字段对不对、严重差错率。
- **一票否决**：比如胡编、漏掉危急项——出现就不许上。

### 第三步：一次只动一大块，方便对比

建议每次主改一类东西：

- 只改 Prompt（措辞、约束、示例）
- 只换模型或参数
- 只改后处理规则（如果业务有规则层）

拿去评审时，别只说「我改了」，尽量带上：

- 改之前 vs 改之后的实验成绩
- 总分，以及原来挂得最多的那几类有没有降下来
- 成本和耗时能不能接受（效果好了但贵三倍，也是产品决策）

### 第四步：线上坏例子要回流进题库

- 客诉、抽检里的坏例子，脱敏后补进评测集。
- 周会优先看「最近常挂的类型」，别只盯一个笼统准确率。
- 日志或 Trace 最好能回放：当时问了模型什么、模型回了什么。

题库不更新，很快就脱离真实业务；能持续补题，调优才有后劲。

## 架构怎么切：别和业务系统揉成一团

产品经理不用管中间件，但要分清谁干什么。

| 层 | 谁用 | 在这套闭环里干什么 |
|----|------|--------------------|
| 评测与调试工作台 | 产品 / 算法 / 测试 | 维护题库、跑实验、改 Prompt、看对比 |
| 接入与调用记录 | 业务研发 | 把线上模型调用留成能复盘的样本 |
| 业务应用 | 终端用户 | 该干什么还干什么；不用把整套业务搬进评测平台 |

关系大概是：

```text
工作台（Prompt · 评测 · 实验）
        │
        │  实验结论、可上线版本
        ▼
业务应用（真实用户）
        │
        │  坏例子 / 调用记录回来
        └──────────► 补进评测集
```

边界说清楚：

- 评测调优管的是：效果有没有变好、能不能证明、发版前能不能再跑一遍。
- 它不管：工单流程、账号权限、业务规则引擎、模型训练本身。

写需求时尽量拆开：「评测能力」和「业务功能」别堆进同一张 PRD，否则优先级永远撕不清。

## 举个例子：视觉质检类场景

比如门店拍照 → 模型识别缺陷 → 汇总成报告（工业质检、巡检类似）：

- 先有评测集：鼓包、扎钉、磨损等类型，再加模糊图、拍歪了、根本没拍到目标等。
- 评估盯关键结果：部位对不对、缺陷有没有漏 / 误报、输出结构合不合法。
- 再调：收紧「看不清就别硬判」、补示例，或对比不同多模态模型。
- 看实验：严重漏检降了多少、误报变了多少、耗时和成本能不能扛。
- 补题：线上漏检工单进题库，避免修一个忘一个。

给产品的建议：先拿一个有对错、能复现的能力把闭环跑通，比空谈「大而全 AI 中台」管用。

## 谁干什么

| 角色 | 主要负责 |
|------|----------|
| 产品经理 | 定题库范围、主指标和上线门槛，排调优优先级，推动坏例子入库 |
| 算法 / Prompt | 设计怎么判分、改 Prompt、看分项为什么挂 |
| 业务研发 | 保证线上能复盘，Prompt 版本和线上一致 |
| 测试 | 发版前跑指定实验；挂掉的转缺陷 |

团队节奏可以约定成：

- **立项**：一个能力 + 一份初始评测集 + 一个主指标。
- **每周**：常挂类型 → 改 → 实验对比 → 再发。
- **治理**：关键 Prompt / 模型变更，必须带实验结论和回滚版本。

## 怎样算真的做起来了

| 阶段 | 你能看见什么 |
|------|--------------|
| 有题可考 | 关键能力有固定评测集和明确主指标 |
| 能对比 | 大改都能拿出「改前 vs 改后」成绩 |
| 有门槛 | 实验不达标不许发版 |
| 能越用越稳 | 线上坏例子稳定进题库，题越来越贴近真实难点 |

## 评审时可以对齐的问题

1. 这一轮只盯哪一个 LLM 能力？（别一次开十个）
2. 评测集谁维护？多久补一次题？
3. 主指标是什么？哪些错误一票否决？
4. 实验低于多少分不许上线？
5. 每次调优是不是尽量只动一类变量，方便对比？
6. 坏例子怎么脱敏、怎么进题库？
7. Prompt / 模型版本怎么和线上对齐？
8. 成本和耗时要不要写进实验结论，而不是只看准确率？

## 结尾

LLM 功能拼到后面，拼的不是「接没接上大模型」，而是：改完能不能证明更好，发版前能不能再考一遍，线上翻车会不会变成下一轮的题。

固定题库考效果，用实验结论决定发不发，把线上坏例子喂回下一轮改进。

团队按这个节奏跑，AI 功能才比较像能长期交付的产品，而不是一次性 Demo。
